# Money Flow Architecture

**Status:** Approved v1 financial control contract; real-money activation remains gated
**Scope:** USD organization-wallet funding, wallet-funded multi-listing checkout, item refunds, disputes, reconciliation, and manual supplier-cost records
**Out of scope:** Supplier payout execution, supplier wallets, customer cash-out, and general ledger

## 1. Financial ownership and currency

Stripe moves external money and supplies evidence about its transaction. GPHKM's immutable ledger owns the customer wallet liability, order debits, wallet refunds, and financial history. A provider balance, browser redirect, success screen, operator note, or caller-supplied ID is never proof for an internal ledger mutation.

V1 uses USD for organizations, wallet funding, orders, and refunds. Stripe charges in USD. Foreign card issuers may convert the charge and apply their own fees. GPHKM absorbs Stripe processing fees and credits the same USD amount as the settled top-up. Finance-triggered allowlisted Stripe snapshots retain the PaymentIntent's charge balance transaction, gross amount, fee, and net alongside refund/dispute balance transactions. A completed payment snapshot is incomplete for resolution when its charge balance transaction is missing or does not match the captured amount/currency. Finance can retrieve Stripe payout and payout-associated balance-transaction facts, then record an append-only comparison against a bank statement amount/date/reference. This is a staff attestation; there is no bank feed integration or independent bank verification.

Amounts use integer minor units or exact decimals, never binary floating point. No multi-currency wallet or local-currency presentment in v1.

## 2. Authoritative financial records

- **Wallet account:** one organization and USD; available balance is a projection of ledger entries and holds.
- **Wallet ledger entry:** append-only funding credit, purchase debit, item refund credit, reversal, or approved adjustment with unique reference, amount, currency, organization, actor/source, and related aggregate.
- **Payment attempt:** immutable funding intent, provider, amount, currency, idempotency fingerprint, state, and external identities.
- **Provider event inbox:** durable verified/rejected event record unique by provider and event identity, with normalized facts and restricted evidence.
- **Access grant:** one organization grant linked to one qualifying settled wallet credit, with start, end/unrestricted state, status, and policy snapshot.
- **Order and items:** parent checkout with per-item purchased terms, wallet allocation, status, and cost snapshots.
- **Dispute and audit records:** provider dispute evidence, holds, resolution, manual supplier transfer evidence, actor, time, and reason.

Never edit or delete posted ledger entries. Corrections are compensating entries linked to the original and approved reason. Reconcile the balance projection to ledger-derived funds and holds.

## 3. Wallet top-up

Only Stripe is enabled for v1. The custom checkout requests a USD amount and creates an immutable payment attempt. Validate configured amount and risk limits server-side. Do not infer payment success from the browser return route. Local funding uses Stripe test keys. Live Stripe API calls require a restricted `rk_live_` key; unrestricted `sk_live_` keys are rejected by the server runtime. Grant only the resources this application calls: Checkout Sessions read/write, Events read, and PaymentIntents, Charges, Refunds, Disputes, Payouts, and Balance Transactions read. Restrict the key to the production server's known outbound IPv4 addresses where available, and store it only in the deployment secret store. Live funding is accepted only when both `GPHKM_REAL_MONEY_ENABLED` and `GPHKM_LAUNCH_GATES_VERIFIED` are explicitly `true`, the secret and publishable key modes match, and webhook event mode matches the configured restricted key. Both flags default to `false`; the launch flag is an operator assertion, not an automated review, and must remain false until every required real-money gate below is evidenced and approved.

The Stripe Node client caps each request at 15 seconds and allows at most one network retry. Session creation uses a stable idempotency key; an outcome that remains unclear stays open for same-key retry or Finance reconciliation rather than being treated as a failed payment.

Before accepting a handled event, verify the signature against the exact request bytes and retrieve the signed event ID through the configured Stripe API client. Require the API-fetched and signed event IDs, type, mode, creation time, and object ID to match; reject connected-account events because Connect is not used. This provider-backed lookup binds the signing secret to the API-key account and blocks settlement when webhook and API credentials come from different merchants. If account lookup fails or identities differ, make no database writes and return an error for reconciliation/retry. Keep this external call outside database transactions.

A verified provider event must also match environment, attempt, organization, amount, currency, and terminal settlement state. Persist and deduplicate the provider event. In one transaction, record the event result, mark the payment attempt settled, post one wallet credit, append audit evidence, create any qualifying access grant, and record notification intent.

Stripe may deliver a delayed Checkout success after another event has already moved the same attempt to `DISPUTED`. When the attempt, Checkout Session, PaymentIntent, amount, currency, and original top-up ledger entry all match, record that distinct provider event as processed without running settlement or posting another wallet credit. If any fact conflicts, link the event to the attempt and open Finance reconciliation; do not change the wallet or dispute state. Duplicate event IDs continue through the normal hash/type conflict checks.

Funding-attempt creation acquires the organization-scoped risk advisory lock, then locks the organization and payment-attempt row. It prechecks Owner authority before taking the advisory lock and rechecks after the organization row lock. Checkout-session attachment and definitive create-failure recording lock the organization before the payment-attempt row and recheck the active Owner. Only a known request rejection is a definitive create failure. Connection errors, provider 5xx responses, idempotency conflicts, and unclassified errors remain open for retry with the same key or reconciliation; do not interpret a cached provider 500 as proof that no session exists. This serializes those commands with Owner removal and organization closure; do not reverse their row-lock order.

New top-up attempts, wallet-funded order checkout, verified Stripe event processing, and Finance risk resolution also serialize on one organization-scoped advisory lock. The webhook acquires it before provider-event, payment-attempt, or wallet locks; checkout acquires it before order and wallet locks; top-up creation acquires it before the organization row lock and attempt insert; Finance acquires it before attempt, case, wallet, or provider-event locks. The order debit and case-opening event therefore have a defined order: either the debit commits first, or the open case is visible and blocks the debit. The shared lock also serializes Finance resolution with duplicate-event identity conflicts that may reopen a case, and Finance's evidence-based Checkout Session absence resolution before it checks for provider events and closes an attempt.

Finance can inspect a read-only queue of open `CREATED` and `PENDING` Stripe attempts, including attempts with no provider event or formal risk case. The queue exposes only attempt and organization IDs, amount/currency, state, timestamps, and whether a Checkout Session ID is recorded. It cannot change an attempt. A missing or delayed provider event requires current provider evidence before a separate, authorized resolution; the queue itself is not proof of payment, failure, or expiry.

If Checkout Session creation has an unknown result and no Session ID was saved, the attempt remains open and holds the one-open-top-up guard. Finance or Super Admin may close it as `FAILED` only after at least 24 hours, verifying in Stripe that neither a Checkout Session nor a payment exists, and recording an evidence reference and reason. Any provider event linked to the attempt blocks this shortcut and must use normal event reconciliation. The command locks the organization before the attempt, appends an audit event, and changes no wallet or ledger row. Never resolve the ambiguity from a timeout, an absent webhook alone, or a customer redirect.

Use idempotency scoped to organization, actor, operation, and normalized request. Provider event ID, provider payment identity, and internal ledger reference are distinct unique identities. Exact replay returns the canonical prior result. Conflicting amount, organization, or event identity fails closed and is alerted. Ambiguous provider outcomes remain pending until reconciled; never create a second charge under a new idempotency identity.

The customer is charged and credited the same USD amount. GPHKM absorbs processing fees and reconciles them separately. No direct provider capture for an order and no split wallet/provider tender in v1.

## 4. Marketplace access grants

One settled top-up whose wallet credit is at least $50 USD qualifies. A pending, failed, promotional, manual, or redirect-only credit does not qualify. The initial access term is six calendar months, starting at settlement; a qualifying top-up during the 15-day trial starts its term immediately. Calculate calendar terms in UTC and clamp month-end dates to the last valid day (for example, six months from August 31 ends on the last day of February).

Each qualifying wallet credit can create only one grant. The grant enables catalog browsing and hidden URLs for its recorded interval. Spending wallet funds does not shorten the grant. Each qualifying top-up creates its own linked grant under the policy active at settlement. With finite grants, the new interval starts at the later of the latest recorded finite expiry or settlement. If the policy is unrestricted, that grant has no expiry. If an unrestricted grant is already active, a later top-up creates a separate grant starting at settlement under the current policy; it does not alter the unrestricted grant or any other interval. Grants keep their recorded intervals if another grant is revoked; access can have a gap until a later recorded interval begins. Do not shift other grants to close gaps.

A pending dispute suspends only its linked grant. A verified loss, refund, or reversal revokes only the linked grant. A dispute win restores the same grant and original expiry; time continues to run while suspended. Global minimum and duration policy is audited, versioned, and applies to future grants only. A Super Admin changes it through a database command that checks the current version, restricts the actor, and appends the audit event atomically; the runtime role cannot update the policy table directly.

## 5. Order checkout and wallet debit

The customer may select up to 25 distinct listings, one placement per listing. At confirmation, revalidate organization membership, catalog entitlement, listing status/revision, terms, price, and available balance. Snapshot placement price and optional GPHKM Writing fee as separate components. For an eligible writing listing, snapshot the Admin-configured two-stage writing fee allocation shown to the customer: first complete draft delivered, then final draft delivered after the included revision. If the customer approves the first draft without requesting a revision, that approval completes both stages. A delivered stage's amount is earned; only the amount allocated to an undelivered stage may be refunded under the disclosed policy.

In one database transaction, create the parent order, all order items and initial item events, immutable purchased listing/content/fulfillment snapshots, one aggregate wallet debit, audit event, and notification intent. The transaction commits all items and debit or none. The retail price snapshot is fixed for the order item; later supplier source-cost or listing-price changes never reprice it. Idempotent replay returns the same order; a reused key with changed intent is rejected.

The wallet balance cannot become negative through ordinary order spending. Use database constraints/locking appropriate to the selected database access layer. Do not rely on a client-calculated total.

## 6. Cancellations, item refunds, and writing

Before the applicable cutoff, a customer may request cancellation of an individual item. The assigned Admin reviews the request and may approve cancellation under the published item and writing-stage policy; the system computes the exact wallet credit. For supplier email, the cutoff is provider acceptance or a staff-recorded manual send; export/preparation alone is not handoff. For platform/internal fulfillment without supplier email, the cutoff is when assigned staff records fulfillment work as started. After the cutoff, customer cancellation and refunds are not allowed by default. Admin staff may investigate a documented Support case and attempt supplier withdrawal where possible. Only Finance or Super Admin may approve an item-specific post-cutoff wallet refund after reviewing the case and evidence; approval is not guaranteed. Legal or processor-required exceptions may require a different remedy. Never issue an external payment refund through this exception path unless that approved exception requires it.

A supplier rejection, nonresponse, or inability to fulfill after handoff is also reviewed by Admin staff through the Support case and does not trigger an automatic refund. Staff may offer an equivalent only with customer approval. If no acceptable equivalent can meet the purchased customer-facing terms, Admin staff handling the Support case may refer an item-specific wallet refund for Finance or Super Admin approval. Other order items continue. Keep the retail price snapshot fixed; source-cost variance affects actual margin, not the customer charge. For an internally fulfilled item, assigned staff records work start; a later cancellation request follows the same post-cutoff Support exception path.

An order-item refund is a new wallet credit linked to the original item debit and approved reason. Total refunds cannot exceed the item's captured retail amount. A canceled item does not refund unrelated items. A wallet refund is not an external Stripe refund.

After valid publication completion, later disappearance alone creates no replacement or refund entitlement, even if caused by a search/platform update. Record the known cause without rewriting original verification evidence. A never-delivered or incorrectly verified placement follows the pre-completion failure policy. Legal or processor-required exceptions remain available.

Writing is a separately priced add-on. The customer receives a draft and one included revision for approval before supplier handoff. Extra revisions require a quote and approval. If the ordering Member declines the final draft while the item is still in customer content review, one database transaction records the writing stop and credits exactly the snapshotted undelivered final stage through a stable item-scoped ledger idempotency key. The placement remains active, but handoff is blocked until a complete customer article passes Admin review and the ordering Member consents to its exact content and current recipient. A later pre-handoff placement cancellation credits only the placement price because the writing stage credit has already been issued. No zero-value ledger entry is created when the final stage was priced at zero.

## 7. Supplier costs, transfer events, and payable coverage

Keep source cost separate from customer wallet accounting. Snapshot a confirmed direct supplier or writing cost to the order item when it is confirmed. Unknown costs remain explicitly unknown; gross-profit reporting is provisional until known. A later correction is a reasoned, audited adjustment, never an overwrite. A source-cost change on an existing order changes its actual margin record, not the locked customer retail price. Reprice the listing only for future orders to preserve the intended margin.

Gross profit is retail revenue after refunds minus confirmed direct source and writing costs. Provider processing fees are shown separately. Optional direct costs may be recorded for platform-owned fulfillment and writing. Do not count unknown as zero.

Finance or Super Admin may record an append-only event only after an actual supplier transfer. Each transfer event records supplier, positive amount, transfer date, unique supplier reference, a required private PDF/EML receipt (maximum 5 MiB), evidence reference, reason, actor, and timestamp, with scoped idempotency and audit events. EML receipts must contain a bounded, structurally valid header block; receipts are never parsed for business facts or rendered inline. The receipt is retained privately, integrity-checked on download, and available only as an audited download to Finance/Super Admin. Database constraints require a receipt for every new transfer and append-only allocations to map the transfer to one or more order items for that supplier. Supplier-sourced listings use the same supplier for source and fulfillment; platform-owned listings may name one external fulfillment supplier. Allocation amounts must sum exactly to the transfer amount. Partial transfers are allowed; there is no `UNPAID` event. Derive unpaid, partially paid, paid, or overpaid by comparing cumulative allocations to the confirmed actual supplier cost for that same supplier and order item. If cost is unknown, show provisional/unknown rather than treating it as zero. Record a real overpayment and flag it for Finance review; never reject or rewrite a transfer that already occurred. Writing costs are not supplier payables unless explicitly attributed to that supplier. These records document manually reported transfers and operator-provided receipts; GPHKM does not execute or independently verify supplier bank payments.

An accepted equivalent changes the operational fulfillment route only; it never rewrites the purchased listing, customer price, or original supplier snapshot. Finance may record actual placement cost against the original supplier, the current supplier, or a supplier on a customer-accepted equivalent route. Pending and declined alternatives are ineligible. Cost corrections are append-only and scoped to item, supplier, and component, so one supplier's correction cannot overwrite another supplier's incurred cost. Writing remains one internal item-level cost chain. Supplier performance attributes each order item once to its current route; timing metrics exclude replaced routes until a route-specific start and turnaround basis is available. Exports retain supplier cost breakdowns and identify provisional or unknown costs; gross profit is emitted only when the required direct costs are confirmed. They do not duplicate revenue or margin across suppliers.

For Stripe Checkout Session creation, persist the first dispatch time before calling Stripe. Stripe may prune API v1 idempotency keys after they are at least 24 hours old ([Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)). Retry the same request with the same key for at most 23 hours from that first dispatch. If the local session ID is still missing after that window, stop creating sessions and leave the attempt in Finance reconciliation; never reuse the key after Stripe may have pruned it.

## 8. Disputes and chargebacks

Create one dispute case linked to the exact funding attempt, wallet credit, and provider dispute identity. Record amount, currency, deadlines, evidence, and state. Hold remaining available funds where possible; suspend the linked access grant and restrict new spending as needed. Do not silently edit the ledger or create an unbounded negative balance.

While an organization has an open Stripe reconciliation case, the database rejects new order debits and new top-up attempts. Existing idempotent retries for a previously created top-up remain available for outcome reconciliation. The customer wallet shows a payment-review notice and zero available-to-spend balance. A verified dispute win restores the linked grant and closes its case only after all disputes are won and no linked provider events remain unresolved. Finance or Super Admin may record a recovery decision only from the latest complete Stripe snapshot refreshed within 15 minutes and tied to a database-issued refresh token. The command reconciles signed principal balance transactions and posts a compensating ledger entry only against funds not protected by other holds. If some loss remains uncovered, the system records the amount and audit decision but keeps the case open, preserves the wallet restriction, and holds remaining available funds. The case closes only when the full provider principal loss is recovered or provider facts show it was reinstated. Provider fees are not debited from the customer wallet. Real-money checkout remains disabled pending provider-mode certification, webhook/refund behavior review, fee/cash-settlement reconciliation, and production security/recovery review.

On a verified win, release the hold and restore the linked grant with its original expiry. On a verified loss, post an authorized compensating ledger entry for the recoverable amount and revoke only the linked grant. If wallet funds cannot cover the full provider principal loss, record uncovered exposure and keep the organization restricted until the remaining amount is recovered or provider facts show it was reinstated. Keep other valid grants unchanged. Reconcile provider dispute events and account restrictions idempotently.

## 9. Reconciliation, audit, and launch gates

The Finance dashboard computes multi-query payable coverage inside one PostgreSQL `REPEATABLE READ` transaction, so a concurrent cost correction or supplier transfer cannot make a single response mix different committed snapshots.

Reconcile provider attempts/events/fees against wallet credits, ledger totals against balance projections, orders/items against debits/refunds, and disputes/holds against provider results. Reconcile supplier transfer allocations against confirmed actual direct supplier costs for the same supplier and order item. One immutable transfer may cover multiple items, but its allocation total must equal its transfer amount. A transfer reference is unique per supplier, case-insensitively after trimming. Show unknown-cost exposure separately; derive unpaid/partial/paid/overpaid states, and flag overpayments for Finance review. Legacy PAID/UNPAID rows remain visible as history but are excluded from transfer totals. Transfer events and allocations are immutable facts and do not execute payouts. A mismatch creates an owned finding; reconciliation never silently edits financial data.

The local Finance scan creates immutable run snapshots and owned findings for wallet projection versus ledger totals, top-up credits and qualifying grants (including valid credits retained during disputes/reversals), order debits, item refund limits/references, active holds, and Stripe events requiring provider review. Finance can append an evidence-backed review outcome to a finding. That records an assessment only; it does not repair source records. The verified webhook's normalized amount/currency/status and payload hash are retained for Finance. Finance can request allowlisted current Stripe snapshots of PaymentIntents, charges, refunds, disputes, payouts, and associated balance transactions; snapshots exclude customer/payment-method details. Resolution requires a matching charge balance transaction for a captured payment. Finance resolution uses signed principal balance transaction amounts, deduplicated by transaction identity, rather than summing cumulative charge refund totals. Fees remain separate and are displayed as provider costs; they never reduce the customer wallet. For payouts, the database verifies balance-transaction totals and preserves Finance's bank-statement amount/date/reference review as append-only evidence; it cannot independently verify a bank statement. An incomplete, stale, mismatched, pending, or open-dispute snapshot cannot resolve a payment-risk case. A staff toggle never replays a payment or marks it settled. Bank data is not imported or independently verified. Supplier transfer receipts are retained and integrity-checked, but actual payment remains a Finance manual attestation and GPHKM does not independently verify supplier bank settlement.

Before real-money production, require:

- U.S. state/entity, Stripe account and merchant configuration.
- Qualified legal/finance approval of wallet, refund, privacy, terms, non-expiring balance, no-cash-out, and legal/processor exception policies.
- Verified webhook signatures, exact matching, idempotency, timeout recovery, sandbox certification, and reconciliation.
- Approved top-up/order risk limits and operational refund/dispute procedures.
- Restricted database roles, RLS, immutable ledger constraints, audit, backups, restore rehearsal, and incident runbooks.

A general ledger is not included unless Finance requires it. Maintain a wallet/order subledger and provider/cost reconciliation exports.
