# Implementation Guide

**Purpose:** Give the team a minimal, reviewable implementation sequence.

## 1. Approved starting architecture

Use one Next.js codebase and PostgreSQL, with customer and staff/admin login and application entry points on separate subdomains. Use Better Auth with Google and verified email/password for customers, with optional TOTP after adding a password. Staff use invitation-bound email/password plus mandatory TOTP or a one-time backup code. A different active Super Admin activates invited staff after verified email and TOTP. Configure `CUSTOMER_APP_URL` and `STAFF_APP_URL` as separate trusted origins with host-only session cookies. Reserve `GPHKM_PUBLIC_BASE_URL` for provider webhook and readiness ingress. Production hostnames, local/staging mappings, and deployment topology are open in O-06. Add one database-backed worker/outbox only when durable retryable or scheduled work is required. Do not introduce Redis, multiple worker lanes, a separate API service, or microservices without evidence that the simpler design no longer works.

Drizzle/Drizzle Kit and local Docker PostgreSQL are accepted for initial development in [ADR-0010](adr/ADR-0010-initial-development-stack.md). Production database placement, private storage configuration, and recovery values remain private launch-time decisions under O-01 and O-02. Before production, validate the restricted database roles, migration path, tenant isolation, connection sizing, and an isolated recovery rehearsal. Use a direct migration connection. Resend is the preferred email provider pending account, sender-domain, webhook, deliverability, and data-handling checks. Local development uses an ignored, permission-restricted filesystem directory configured by an absolute `GPHKM_PRIVATE_STORAGE_PATH`; production uses private object storage and fails closed unless explicitly configured. Keep provider/account settings and recovery details in the private operations record. The staff customer directory uses the PostgreSQL `pg_trgm` extension; migration 0146 creates it and the supporting directory and import indexes. Migration 0147 fixes a reserved-word collision in the audited membership-role update. Migration 0148 separates literal name, email, and organization search branches and limits detail aggregation to the requested page; migration 0151 caps offset pagination at the newest 100,000 matching customers. The main application pool size is configurable from 1–50 through `GPHKM_DB_POOL_MAX`, defaulting to 5 until O-01 deployment sizing is complete.

Customer notification mail shares the approved Resend provider boundary but has a dedicated PostgreSQL worker identity and outbox path. Keep `GPHKM_RESEND_DATA_HANDLING_APPROVED=false` and do not run `npm run worker:notifications` until the provider account, sender domain, signed webhook endpoint, and data-handling review are complete. Set the worker's database URL and provider configuration only in the deployment secret store. The worker checks Resend configuration at startup, uses provider idempotency within its retention window, and puts ambiguous outcomes in Super Admin reconciliation; it never blindly retries an unknown send. Customer email can be disabled per user while in-app notices remain enabled. See [Operations and quality standards](OPERATIONS_AND_QUALITY.md) for production process management.

### Auth verification

Apply migrations and start the app with a disposable loopback PostgreSQL database and synthetic identities. Run:

```sh
npm run db:migrate
npm run db:check-rls:local
npm run db:check-staff-auth:local
npm run db:check-auth-recovery:local
npm test
npm run typecheck
npm run lint
npx drizzle-kit check
git diff --check
```

The staff auth check exercises invitation-bound signup and acceptance, local bypass behavior, staff access, and customer/staff host isolation. The MFA check requires the `gphkm_staff_mfa_check` loopback database, all three database roles on that database, and an isolated app on port 3001; it exercises invited-account TOTP setup before activation, the password challenge, backup-code recovery, exact-session proof, and surface isolation. It removes temporary credentials and staff authority; immutable audit evidence retains inert synthetic identities, so use only the dedicated disposable database. The auth recovery script also requires a disposable database and removes its temporary HTTP fixture accounts. It verifies that a second Super Admin can reset another staff account's factor and sessions both after enrollment and before TOTP enrollment. The Staff Access page exposes that audited reset to every other staff account, while preventing self-reset. Use distinct HTTPS placeholder app origins and test database URLs for the production build. MFA-mode staff auth requires `MFA_PROOF_DATABASE_URL` to use the restricted `gphkm_mfa_proof` role.

**PASS — staging review draft:** the staging-only draft Terms and Privacy pages are available for inspection. They are clearly labeled as drafts and cannot satisfy production legal approval.

**PENDING — staging email:** exercise customer verification, password reset, and a staff invitation through the deployed worker using real acceptance-test inboxes. A successful local synthetic send does not count as staging delivery.

**PENDING — Google:** exercise customer signup and login with both an allowed and a non-listed Google account. Confirm the provider audience configuration permits the intended staging audience and that production stays separately gated.

To run the local customer email auth check, migrate a fresh disposable PostgreSQL database and export its migration and runtime URLs. Build with HTTPS placeholder origins, then run:

```sh
npm run db:check-customer-auth-email:local
```

This check captures synthetic messages in memory, verifies legal consent, and exercises customer verification-link expiry, surface binding, idempotent rapid resends, passive confirmation-page reads, concurrent redemption, tombstone persistence, replay rejection, and session creation. ## 3. Implementation rules

- Never trust browser-supplied price, total, role, wallet balance, supplier assignment, entitlement, or order status.
- Recheck active organization membership and staff permission for each sensitive read and command. Enforce item-level assignment before exposing order content/evidence.
- Keep exact money, immutable ledger entries, scoped idempotency, atomic transactions, and database uniqueness.
- Do not make external calls inside retryable database transactions. Persist work and retry with stable idempotency.
- Keep customer, supplier, finance, and admin data projections separate and allowlisted.
- Keep internal fulfillment states and packet transport states separate from customer-visible GPHKM-branded milestones; never expose supplier identity or source classification.
- Do not use UI route visibility as authorization. RLS is defense in depth, not a substitute for application checks.
- Do not add generalized workflow engines, permission builders, payout modules, or status override commands without a concrete approved need.
- Keep each security, money, import/export, or publication policy in one canonical document and link to it elsewhere.
