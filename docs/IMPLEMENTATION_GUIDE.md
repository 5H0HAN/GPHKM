# Implementation Guide

**Purpose:** Give the team a minimal, reviewable implementation sequence.

## 1. Approved starting architecture

Use one Next.js codebase and PostgreSQL, with customer and staff/admin login and application entry points on separate subdomains. Use Better Auth with Google and customer-only verified email/password. Keep host-only session cookies and exact trusted origins; subdomains do not replace role, membership, or MFA checks. Exact hostnames, OAuth callbacks, local/staging domain setup, and shared-versus-separate deployment are open in O-06. Add one database-backed worker/outbox only when durable retryable or scheduled work is required. Do not introduce Redis, multiple worker lanes, a separate API service, or microservices without evidence that the simpler design no longer works.

Drizzle/Drizzle Kit and local Docker PostgreSQL are accepted for initial development in [ADR-0010](adr/ADR-0010-initial-development-stack.md). Coolify + Neon remain the preferred production direction, subject to the RLS, transaction, cost, and recovery proof in O-01. Use a direct migration connection. Resend is the preferred supplier email provider pending account, sender-domain, webhook, deliverability, and data-handling checks. Local development uses an ignored, permission-restricted filesystem directory configured by an absolute `GPHKM_PRIVATE_STORAGE_PATH`; production private object storage remains gated by O-02.

Customer notification mail shares the approved Resend provider boundary but has a dedicated PostgreSQL worker identity and outbox path. Keep `GPHKM_RESEND_DATA_HANDLING_APPROVED=false` and do not run `npm run worker:notifications` until the provider account, sender domain, signed webhook endpoint, and data-handling review are complete. Set the worker's database URL and provider configuration only in the deployment secret store. The worker checks Resend configuration at startup, uses provider idempotency within its retention window, and puts ambiguous outcomes in Super Admin reconciliation; it never blindly retries an unknown send. Customer email can be disabled per user while in-app notices remain enabled. See [Operations and quality standards](OPERATIONS_AND_QUALITY.md) for production process management.

### Slice 4 — Multi-listing orders

### Slice 5 — Fulfillment, evidence, and reporting

Implement assigned fulfillment with explicit item transitions, the packet lifecycle, item-level readiness, exact recipient/content preview, server-side provider send, manual export/attestation/evidence, supplier acknowledgement, delivery-event reconciliation, and exception queue defined in [Supplier Email Handoff](SUPPLIER_HANDOFF.md). **Exit:** no silent substitution; supplier identity remains private; internal JSON exports are Super Admin-only; post-completion link disappearance creates no replacement/refund entitlement; cost/margin stays provisional until actual costs are recorded.

### Slice 6 — Production readiness

Complete provider certification, security and threat-model review, qualified legal/finance review, support runbooks, monitoring, backup restore, rate/volume limits, and real-money launch gates.

**Exit:** real-money checkout remains disabled until the state/entity, provider account, and legal/finance requirements in OPEN_DECISIONS.md are resolved.

## 3. Implementation rules

- Never trust browser-supplied price, total, role, wallet balance, supplier assignment, entitlement, or order status.
- Recheck active organization membership and staff permission for each sensitive read and command. Enforce item-level assignment before exposing order content/evidence.
- Keep exact money, immutable ledger entries, scoped idempotency, atomic transactions, and database uniqueness.
- Do not make external calls inside retryable database transactions. Persist work and retry with stable idempotency.
- Keep customer, supplier, finance, and admin data projections separate and allowlisted.
- Keep internal fulfillment states and packet transport states separate from customer-visible GPHKM-branded milestones; never expose supplier identity or source classification.
- Do not use UI route visibility as authorization. RLS is defense in depth, not a substitute for application checks.
- Do not add generalized workflow engines, permission builders, payout modules, or status override commands without a concrete approved need.
- Keep each security, money, import/export, or publication policy in one canonical document and link to it elsewhere.
