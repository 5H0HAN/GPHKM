# Security Baseline

**Status:** Required implementation baseline
**Scope:** Customer organizations, admin operations, supplier confidentiality, wallet integrity, imports, publication evidence, and payment integrations.

## 1. Identity and session security

- Use Better Auth for customer Google and verified email/password sign-in. Keep staff on its separate host and do not enable public staff signup or staff password reset.
- Set `BETTER_AUTH_SECRET` from at least 32 cryptographically random bytes (base64 or hex). Production auth rejects noncanonical encodings, short values, and low-diversity byte sequences; local-only auth retains a length check for test fixtures. Never use an example, phrase, or checked-in secret.
- Local `.test` email/password fixtures still require both `NODE_ENV=development` and explicit `GPHKM_LOCAL_AUTH_ENABLED=true`; reject that flag elsewhere. Bootstrap reserved fixtures once through the loopback-only CLI with env-supplied secrets. Public customer credential signup is disabled in development and only enabled in deployed environments when transactional email configuration and data-handling approval are present. Require email verification before credential sign-in. See [ADR-0011](adr/ADR-0011-local-auth-test-fixtures.md) and [ADR-0018](adr/ADR-0018-customer-email-password-auth.md).
- `GPHKM_LOCAL_MFA_DISABLED=true` is an optional local testing exception and is accepted only when `NODE_ENV=development` and `GPHKM_LOCAL_AUTH_ENABLED=true`; reject it in every other environment and keep it `false` by default in `.env.example`. In this mode only the staff TOTP challenge and session-proof requirement are skipped. The staff identity must still be active and every staff permission, item assignment, RLS boundary, and audit rule still applies. Production always requires verified MFA and exact session proof.
- Verified signup creates an organization and first Owner. Users may belong to multiple organizations with an explicit active organization context. Organization invitations are email-bound, accepted by the same verified address, expire after seven days, and default to Member. Protect the last Owner from removal until ownership is transferred. Invitation tokens are one-time, hashed for acceptance, and separately AES-256-GCM encrypted only in the restricted delivery outbox. Use URL fragments plus explicit authenticated POST; never accept on GET or place the token in a query string, logs, analytics, or ordinary page data. Unknown sends are not retried automatically.
- Require verified customer identity before catalog access and wallet funding.
- Credential password reset uses a short-lived Better Auth token sent only through the approved transactional email provider. Put the token in the URL fragment so it is not sent in the HTTP request, set `Referrer-Policy: no-referrer` on the reset page, use generic responses that do not enumerate accounts, persistent auth rate limits, and revoke all existing sessions after reset. Never log the reset URL/token or expose it outside the mail body. Google-only accounts use Google recovery. Staff reset and support-managed identity recovery remain disabled.
- Use secure cookies, appropriate CSRF/origin checks, persistent database-backed rate limits, safe redirects, prompt revocation, and recovery controls. Keep customer and staff authentication rate-limit buckets separate so abuse against one surface cannot consume the other's sign-in allowance. Production auth requires `GPHKM_TRUSTED_PROXY_CIDRS`; configure only the actual proxy hops that may appear in `X-Forwarded-For`, and ensure the app origin is reachable only through those proxies. Before deployment, verify the proxy overwrites or sanitizes client-IP headers and test the configured chain.
- Customer session metadata is shown through an account-scoped server projection that omits session tokens. Every built-in session revocation route (single, other sessions, or all sessions) is guarded by the shared Better Auth hook and requires a session created within the last 10 minutes; missing or invalid session metadata fails closed. Bulk revocation also invokes Better Auth's fresh-session endpoint before the less restrictive revoke endpoint. Session listing remains available without recent authentication.
- Serve customer and staff/admin login from separate subdomains with exact per-environment trusted-origin allowlists. Keep Better Auth cross-subdomain cookies disabled and use host-only session cookies. Never broaden cookies to the parent domain for convenience. A hostname is not an authorization boundary: recheck organization membership or staff role, MFA outside the explicit local exception, and item assignment server-side on every protected request. Configure each OAuth callback explicitly; do not trust wildcard subdomains or arbitrary forwarded hosts. The bare local development host serves only the product landing page; direct local customer/staff routes redirect to their configured authentication hosts.
- Enforce exclusive customer/staff principal domains: a principal with any staff account cannot receive customer organization membership, and a principal with any customer membership cannot be provisioned as staff. Database triggers serialize first membership and staff-account creation on the auth principal row; request authorization and sign-in projections reject a staff identity forwarded to the customer host and vice versa. Invitation and signup handlers provide an early user-facing rejection. Disable public staff signup; bootstrap the first Super Admin through a one-time controlled setup, then use Super Admin invitations that expire after seven days. Ordinary staff hold only one of Admin or Finance; Super Admin is the only all-access role. Staff invitation acceptance creates an inactive account; require verified TOTP and Super Admin activation before granting authority. Pending/deactivated staff may establish a staff-host session to enroll or verify MFA, but every protected command still requires an active account and exact session proof. Revoke sessions on deactivation.
- Do not grant the request runtime direct UPDATE authority over `staff_account` or `organization_member`. Route activation, deactivation, role changes, member promotion/removal, and invitation acceptance through narrow database commands that enforce the valid transition, last-active-Super-Admin/last-Owner rules, session revocation where required, and append-only audit in the same transaction. Recheck actor authority after acquiring the locks that serialize authority transitions; application checks before the transaction are not enough. Limit first-Owner membership insertion to the verified account that created the organization. Staff-host OAuth may create a user only when that verified email has a current pending staff invitation.
- Store accepted Terms and Privacy versions, actor, and timestamp. Newsletter opt-in is separate, optional, default-off, and revocable.

## 2. Authorization and tenant isolation

- Deny by default and check current organization membership or staff permission at every sensitive read and mutation.
- Customer tenant scope is derived from active membership; never authorize by object ID alone.
- Use PostgreSQL RLS for organization-owned records with restricted runtime roles and trusted transaction-scoped tenant context. Application checks remain mandatory.
- Provision application, worker, webhook, and MFA-proof roles as `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS`; grant only the database and schema/table/function privileges each role needs. Do not grant the application role membership in privileged roles.
- Keep payment and email-provider event processing and staff MFA proof writes outside the general request runtime role. Stripe, Resend, and MFA proof writes use distinct, narrowly granted database identities; Resend can process only its fulfillment and notification callback commands and cannot call Stripe wallet functions. Do not treat caller-settable database GUCs as proof of a provider signature or MFA result.
- Customer and staff responses use explicit allowlisted projections. RLS does not redact columns.
- Customer order milestone history is an append-only allowlisted projection. Database triggers capture only public status and next-update changes; RLS limits reads to authorized organization members and assigned staff, and the runtime cannot insert, update, or delete history.
- Organization members may read the shared wallet balance, but only Owners may read transaction-level ledger, top-up-attempt, and hold rows. Members use a membership-checked aggregate projection to calculate available funds and order sufficiency without receiving hold records or recharge history.
- Admin manages catalog and routine fulfillment; Finance handles restricted financial/cost work; Super Admin has broad access but cannot bypass RLS, ledger, evidence, idempotency, or audit.
- Internal JSON reports are Super Admin-only. Assigned Admin handoffs are minimum-data, purpose-bound, and audited. Gross-profit and source-cost fields require cost permission.

## 3. Marketplace access and URL confidentiality

- Compute the 15-day organization trial and paid access grants from server timestamps.
- Keep raw grant intervals behind Owner-only wallet history; Members receive only a tenant-checked active-access decision for catalog and checkout.
- Grant access only from verified, settled wallet credits meeting the $50 policy. Link each grant uniquely to its funding credit and policy version.
- Access is independent of wallet balance. Dispute/reversal affects only the linked grant; preserve other grant intervals.
- Check entitlement before returning catalog rows, URL, counts, search results, page metadata, hydration/prefetch data, exports, or analytics payloads.
- A public-listing flag bypasses URL concealment only while browsing is allowed. It never bypasses sign-in or the post-trial access gate.
- Do not deliver protected data behind a blur or rely on client-side route checks. An expired-access screen may use only generic, non-interactive placeholder shapes behind a blur; never render inaccessible listings or hidden URLs. Prevent shared caching of organization-specific catalog responses.

## 4. Wallet, payment, and idempotency

- Treat the wallet as an immutable ledger, never an editable balance field.
- Use exact USD minor units, atomic transactions, uniqueness constraints, and scoped idempotency for top-ups, orders, refunds, access grants, and retryable financial commands.
- Verify Stripe webhook signatures from exact request bytes, then retrieve each handled signed event through the configured Stripe API client and compare event identity before accepting facts. This binds the webhook secret to the API-key account; reject Connect account events because GPHKM does not use Connect. Match environment, attempt, organization, amount, currency, and terminal state. Redirects do not prove payment.
- Keep provider account verification outside retryable database transactions. Use a separate database connection for webhook event processing after signature and account verification. The general runtime identity must not have execute permission on wallet-crediting event functions. Keep wallet grant calendar arithmetic pinned to UTC.
- Persist provider events durably and deduplicate by provider identity. Ambiguous timeouts are reconciled before retry; never guess.
- Multi-item order creation and aggregate wallet debit commit atomically. Item refunds are compensating wallet credits and cannot exceed item retail value.
- Chargebacks hold available funds where possible, suspend linked access, and restrict spending as policy requires. Never silently mutate the ledger.
- Store provider fees separately. Do not implement supplier payout execution or customer cash-out.

## 5. Supplier, import, and content protection

- Supplier identity, contacts, source rates, source files, import values, internal notes, and source classification are confidential.
- Only Admin/authorized staff access supplier contacts for inventory or assigned fulfillment. Finance sees source costs as permitted; exports require exact role.
- Fulfillment updates are item-scoped in RLS. Runtime SQL has column-level UPDATE only for workflow fields; it cannot edit item/order identity, assignment, or creation metadata. Assignment uses a locked SECURITY DEFINER command that validates active Admin/Super Admin authority and the target Admin, then writes the assignment and immutable audit event atomically. Application commands remain responsible for allowed lifecycle transitions and their reasoned audit events.
- Assignment locks the actor and target staff authority rows in stable ID order and rechecks both roles after locking. Deactivation locks the target staff row before checking for active assignments. A staff member with active fulfillment work cannot be deactivated until the work is reassigned; assignment by a revoked actor or to an inactive/non-Admin account is rejected.
- Content-sharing consent is serialized against handoff using the locked fulfillment row as the cutoff authority. Do not make this decision from a second helper query whose snapshot may predate a concurrent handoff. A local two-session regression test covers both commit orders.
- CSV/XLSX and public Sheets data are untrusted. Use a maintained parser in data-only mode; bound file size, rows, worksheets, archive expansion, parsing time, parser memory, and cell lengths. Run XLSX archive inspection and parsing in a terminable worker thread with fixed memory and time limits, and allow only one active XLSX parser per application process. Fail additional requests promptly so per-worker memory cannot multiply without limit. Reject formula cells and macro-enabled formats; never execute macros, formulas, embedded links, or external workbook references. Escape rendered values and protect CSV/XLSX exports from spreadsheet formula injection. Review/correct staged rows and apply only selected valid rows; invalid and duplicate-flagged rows remain staged. These controls are the v1 baseline; an external antivirus service is not required unless a later threat review or hosting requirement justifies it.
- Customer order details and supplements are text-only in v1; provide no customer file-upload endpoint for articles, briefs, or order evidence. Enforce field-specific length and structured-value validation, store input as data, and contextually encode it in every UI, email, EML, and PDF output. Do not interpret customer text as HTML, scripts, templates, or executable markup.
- Direct Sheets reads are limited to public/readable sources and staff-triggered staging refresh. Accept only a validated Google Sheets URL/ID and fetch through fixed Google endpoints; reject arbitrary hosts and unvalidated redirects. Never fetch URLs from cells or other user-controlled fields.
- Treat provider responses as untrusted input. Resend JSON responses require an `application/json` content type and are streamed under a 256 KiB limit; fixed-provider requests reject redirects and use explicit timeouts.
- Supplier handoff includes only the article/brief and publication instructions required for the assigned order, with customer notice/consent. Exclude name, account, and billing details.
- Organization billing profiles contain only optional legal name, billing email, and billing address. Expose them only to active Owners through an Owner-scoped RLS policy and guarded update command. Do not expose them to Members, staff, suppliers, reports, logs, or generic audit metadata. Audit changed field names, actor, organization, and time without recording values.
- Keep customer article content out of logs, traces, analytics, and generic exports. In local development, store staff import files, handoff evidence, and mandatory supplier-transfer receipts in the configured private filesystem directory; production must use a private object-storage provider with access metadata in PostgreSQL, access audits, authenticated download-only delivery, and approved retention/deletion rules. Do not serve uploaded evidence as active inline content.
- Supplier transfer receipts are PDF/EML only, capped at 5 MiB, stored privately, hash-checked on download, and available only to Finance/Super Admin through audited attachment downloads. Transfer and receipt metadata must commit atomically; runtime updates/deletes are revoked, and receipt records are append-only. A staff-provided receipt is not independent proof of bank settlement.
- Treat uploaded receipt bytes as untrusted. Extension, signature, and size checks do not certify file safety; never render them inline or parse their contents. If the database commit outcome is ambiguous, retain the private file for reconciliation rather than risking deletion of evidence referenced by a committed transfer.

## 6. Supplier handoff and email

- Follow the packet boundary in [Supplier Email Handoff](SUPPLIER_HANDOFF.md): one organization/order/supplier/assigned Admin per packet, based on the order's supplier assignment snapshot.
- Require item readiness, final approved content, recipient review, and current consent to share content with the publication-site/fulfillment partner before dispatch. Internally bind that consent to the exact content, supplier, and recipient; never expose supplier identity to the customer.
- Admin assigned to fulfillment or Super Admin may send from the configured server-side provider or export a packet for manual sending. Export is not proof of handoff.
- Persist packet version and send intent before external calls. Unknown send outcomes require reconciliation before resend; retries and webhooks are idempotent and audited.
- Verify webhook signatures and deduplicate event IDs. Keep provider acceptance/delivery distinct from supplier acknowledgement and publication completion.
- A signed bounce/failure event still proves provider acceptance for the ordinary-cancellation cutoff. Its provider audit insert is restricted to the exact Resend message reference and order item; it does not advance the customer milestone.
- Restrict packet snapshots, manual evidence, recipient details, and article content to authorized staff. Do not place content in generic audit logs.
- Invitation delivery shares the existing gated Resend worker but uses a separate outbox. Runtime may enqueue and read only delivery status; only the restricted worker can claim encrypted invitation tokens. Revocation/acceptance/expiry invalidates queued sends, and acceptance always rechecks current status and expiry under row lock.

## 7. Metrics and publication evidence

- Metric API credentials remain in a secret store and are accessible only to the server/worker paths that need them.
- Only Super Admin may record a current-observation redistribution attestation. Attribution, bounded evidence reference, review reason, actor, observation, listing, and provider are recorded through an append-only event/audit pair. This internal attestation does not prove legal rights; keep customer display disabled until external L-05 review is complete.
- Store metric provider, scope, value, source date, refresh time, and status. Missing, stale, failed, and zero are distinct.
- Verify licensing, attribution, and redistribution terms before customer display.
- Open PageRank uses a fixed provider endpoint, validates bare domain input, rejects redirects, and never fetches the target website; Ahrefs/Moz remain disabled until separately configured and reviewed.
- Staff verification records the live URL, timestamp, method, verifier, and evidence. The database permits evidence only in link-verification states; completing an incorrect-verification correction requires paired audit/history events and the newest evidence. Only one unresolved correction is allowed per item. Google indexing is separate and is unknown unless authorized Search Console data exists.
- Do not perform automated URL fetching until SSRF defenses are designed and reviewed.

## 8. Audit, monitoring, and retention

Audit staff permission changes, organization membership/invitation/ownership changes, fulfillment assignment changes, listing price/live changes, imports/applies, supplier-contact access, packet preparation/versioning, automatic/manual handoffs, recipient overrides, send outcomes, acknowledgements, access-policy changes, wallet postings/reversals/refunds, provider-event outcomes, cost corrections, supplier transfer events, Support case decisions, exports, and publication verification.

Audit records include actor, tenant/target, timestamp, action, reason, outcome, and safe correlation identifiers. Redact credentials, payment payloads, supplier secrets, customer names where not required, and article/brief content.

Audit events are append-only for all application roles, including Super Admin. Routine runtime roles cannot update or delete audit events. Correct mistakes with a new linked event; any exceptional data-retention purge must be separately authorized and leave permitted evidence of the purge.

Retain financial and audit evidence as required by law. Retain final order/publication records as needed. Customer order content is text-only, with no customer-uploaded order attachments in v1. Minimize or delete private briefs and drafts after fulfillment/dispute needs end. Apply separate access and retention controls to staff inventory uploads, staff-only handoff evidence, and GPHKM-generated packet PDFs. Set exact periods with legal/finance before production.

## 9. Security acceptance

Before real-money production, demonstrate cross-organization denial, staff-role isolation, hidden-field exclusion, active entitlement checks, webhook replay safety, exact money matching, concurrent wallet-spend safety, item refund bounds, safe import staging/export, audit delivery, backup restoration, and incident response. Test RLS with the restricted runtime identity, not a database owner.
